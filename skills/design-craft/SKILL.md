# design-craft

## 用途

`design-loop` 管怎么写、怎么查、怎么发；这一份管画什么、怎么判断画得好不好。站主没有设计经验，用自然语言指挥：方向要由 Agent 摆出来让站主挑，不能只交一个「稳妥」的答案。

为什么要有这一份：到 v1.0 计划的 Phase 5 里，Claude、Codex、Argon 三家拿同一份简报给 Pith 做方案，第一轮几乎画成了同一个样子（旧纸或暖米纸的底、苔绿、一个暖色点缀、衬线标题、植物发芽的动效），最后一轮的骨架也都是「左栏 + 对话 + 右栏」。工具没卡住谁，是说明里只有流程、没有设计判断。

## 输入

- 简报：照同目录的 `brief-template.md` 写（站主说的话、参照、反例、要避开的默认、真实内容、第一轮交什么）。简报缺项就先补，或者用提问功能问站主。
- 方案已经定了的东西：`schemes/<方案>/DESIGN.md`。还没有方案就当作空白。
- 真实的内容和任务：用这个产品的人真的会看到的字和数据。

## 一、先发散，再收敛

1. **第一轮只摆方向，2–4 个，低保真。** 真实内容、真实尺寸，颜色先用灰阶加一个强调色，字体先用一两种。目的是让站主挑方向，不是交成品；配色、字体细节、token、Design System 都等方向挑定再做。
2. **方向要真的不同。** 不同在骨架和空间组织（分栏还是整页、列表还是画布、密还是疏）、主要形状（线、块、卡片、节点）、信息的组织方式、动效的性格。只换颜色、换字体、换圆角，不算一个新方向。自查：**把颜色和字体都遮掉，还分得出几个方向？** 分不出就重来。
3. **每个方向叫得出名字，押一个注。** 一句话说清它是什么（「页边：没有框，出处是脚注」），再说它押在哪一点上：一个形状、一种排版手法、一个动效时刻。说不出押注的方向，往往就是默认审美。
4. **写清每个方向的代价。** 每个方向都写它的好处和最大的代价，喜欢的那个也一样；不要只替一个方向说话。
5. **挑定以后再细化。** 站主挑了方向（或说了怎么拼），下一轮才定配色、字体、动效的数值，进 R 页、建方案。

## 二、点名默认惯性

下面这些是模型（包括 Claude）不加约束时最容易落进去的样子。用了任何一条，都要在交付说明里写为什么这个产品非它不可；一个方向里用了两条以上，多半就是没想过。

- 米色、旧纸、奶油色的底，配衬线标题和陶土色、柿色、砖红的点缀。
- 苔绿、鼠尾草绿，「生长、发芽、花园」的隐喻直接画成植物。
- 左栏 + 中栏 + 右栏的三栏骨架，每栏一样的密度。
- 圆角卡片加左边一道彩色竖条；处处是浅灰描边的卡片。
- 渐变底、光晕、玻璃拟态、发光。
- 满屏的小动效：每个悬停都弹一下，却没有一个让人记住的时刻。
- emoji 当图标；一堆没人要的数字、标签、徽章（data slop）。

简报里的形容词（「淡雅、简约、温暖、有书卷气」）常常正好指向这些默认。遇到这种简报，至少摆一个明显不在默认里的方向，给站主一个真的选择。

## 三、做出记忆点

- **字体**：从内容和气质出发选，一套最多两三个家族；中文、西文各自分 Display 和 Body，数字和符号跟西文 Body。可再分发许可才能打包（`docs/licensing.md`）；探索阶段直接用 Google Fonts 托管的就好。
- **颜色**：一个主导色（底或结构），零到两个强调色；强调色明度相近、色相不同。颜色要有分工（结构、交互、状态各管各的），不平均撒。对比度：探索阶段跑一下 APCA，不过就在交付说明里写出来；进 R 页、建方案必须全过（正文 Lc ≥ 75，次要文字和交互色 Lc ≥ 60，明暗都验）。
- **空间**：大胆的留白或有控制的高密度，二选一，别平均用力；可以不对称、可以跨栏。
- **图形**：一套方向里，容器、分隔、图标、状态、动效最好是同一种形状语言（比如全是线、全是卡片、全是软色块），而不是各用各的。
- **动效**：集中在一两个编排好的时刻，比满屏小动静好得多。动效要表达状态的变化（研究在进行、出处连上了、成果收起来了），不是装饰。读字的地方保持安静；每个动效都要有减弱动态效果时的终态（`docs/motion-tiers.md`）。

## 四、内容

- 用真实或接近真实的内容，不写 lorem ipsum；缺的事实写成 `[待填]` 这样的占位，不编数字、不编引文。
- 画「一条真的任务」，比画几张静态页更能看出好坏：从一个真实的起点走到结果，中间的状态、出错、确认都露出来。
- 每个元素都要有存在的理由；版面空，是构图要解决的问题，不是加内容的理由。

## 五、能点的原型

- 方向挑到需要比交互的时候，一个方向一张能点的板：几屏放在同一张板里、共用一份状态（每屏一个 `<sc-if>`），任务能从头走到尾，设置能影响主流程。
- 用画布的模板写（`<x-dc>`、`renderVals()`、`<sc-if>`、`<sc-for>`、事件绑定），不要用外挂脚本去生成界面：那样在 Claude 云端的编辑器里改不了。写法见 `design-loop` 和 `bench/README.md`。
- 每个方向自己的配色、字体、动效、图标是一整套，不要做成「同一套界面 + Tweaks 换颜色」。Tweaks 只放明暗、开在哪一屏这类开关。

## 六、自己先看，再交

- `node bench/bin/dw.js check <画布名>`：静态终态、版面问题，截图要看。
- `node bench/bin/dw.js frames <画布名> --board <文件>`：按时间线截几帧拼成一张总览，看动效是不是你想的那样（要先点一下才会动的，加 `--click <按钮上的字>`）。
- 看的时候问自己：遮住颜色还分得出方向吗？一屏的信息量对吗？押注的那一点一眼看得到吗？用了哪几条默认惯性？

## 七、评估几家的版本

- 先遮住颜色和字体看骨架，再看图形语言是否贯穿，再看押注、信息密度、动效的时刻，最后才看配色和字体。
- 每家写长处、短处和它落进了哪几条默认惯性；结论写进画布的 `README.md` 或交接文档，不只留在对话里。

## 输出

- 画板（`canvases/<画布名>/project/`）和这一页的说明。
- 交付说明写：每个方向一句话、押注、代价；用了哪几条默认惯性、为什么；对比度没过的配对（探索阶段）；没目视的部分。

## 验证

- 遮色自查做过：几个方向在骨架或形状语言上确实不同。
- `dw check` 全过、截图看过；有动效的板 `dw frames` 看过，节奏和手感留给站主目视。
- 交付说明里有押注、代价和默认惯性那一段。
